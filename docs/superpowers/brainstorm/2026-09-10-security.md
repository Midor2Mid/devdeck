# Boundaries — what a public repo and five foreign machines change

Seat: security. Date: 2026-09-10. Input: `.superpowers/HANDOFF.md` §4, `src/main/{server,guards,http,files,devices,db,mcptools,mcpserver,checks,netproxy,redact,diagnostics,pty}.ts`, `src/main/index.ts`'s hardening block, `tests/{server-guards,http-ssrf,db-readonly,dbFileApproval,publishedIdentifiers}.test.ts`.

The app was not launched (a `performance-analyst` holds the single-instance lock). Everything below that is called *proven* was proven by running code against the real modules; everything else is labelled.

---

## Verdict

**Through.**

Two holes, both reachable without the author's cooperation, both demonstrated with running tests:

1. **The relayed-HTTP SSRF guard is bypassable.** `isBlockedAddress` enumerates exactly one IPv4-in-IPv6 embedding (`::ffff:/96`) and answers *allowed* for every other one. Five spellings of loopback / RFC-1918 / `169.254.169.254` walk through `httpSend({ guardRemote: true })`, and so does an attacker-controlled `AAAA` record and a redirect hop. This is the `[::ffff:7f00:1]` bug again, in the spellings that were not thought of.
2. **An unauthenticated LAN client can stall the main process.** `GET /xterm.js` is served *before* `authFor` and re-reads 488 KB from disk synchronously on every request. Measured at 3.45 ms per call warm — **290 requests/second fully blocks the event loop** that relays every PTY byte and answers every IPC call. No token, no throttle.

Nothing blocks the beta *by itself*, on one condition, stated in §5: the remote server ships **off by default**. If it ships on, finding **F-1 blocks** — it is a proven remote SSRF, on a network the author does not control, with the source that explains the guard now public.

## 1. What the public repo re-prices

Most guards here never depended on secrecy and are unchanged by publication: `tokenOk` (hash-then-`timingSafeEqual`), `chooseBind` (refuses rather than widening), `isExpired` (a literal `0` is the only "never"), the cookie name/`__Host-` handling, `isWithinRoots`'s realpath of both sides, and the decision protocol (minted in main for a waiting session, hashed against the tail, spent once). Those are algorithms. Reading them teaches an attacker that they are correct.

**What did quietly depend on nobody reading: every enumeration.** `blockedV4`'s six ranges. `isBlockedAddress`'s one IPv6 embedding. `CREDENTIAL_HEADERS`'s four names. `redact.ts`'s rule list. `IGNORE`'s nine directory names. An enumeration is only as good as the imagination of whoever wrote it, and the reader is now everyone. F-1 is exactly this failure, and the comment above it makes it worse rather than better: telling a reader that `::ffff:/96` *was* thought about tells them precisely which embeddings were not.

The costs accepted in §4, re-priced:

- **CGNAT `100.64.0.0/10` deliberately unblocked.** Priced as "that is where the tailnet lives, and a tailnet peer is not a loopback". True on one machine that runs Tailscale. On five foreign machines, 100.64/10 is also where several consumer ISPs and fixed-wireless providers put their subscribers, and where some managed corporate estates sit. The paired phone can relay HTTP into that shared segment. **Re-price from "adds nothing" to "reaches the beta user's ISP-shared segment."** I would still *not* block it — that breaks the tailnet bind this feature is built around — but the Remote panel should say which segment the current bind exposes, and `tests/server-guards.test.ts:52` should carry the reason rather than just the expectation.
- **DNS rebinding, named and not attempted.** The reasoning is right and the write-up is honest, and publication now hands an attacker the paragraph. Still not a pre-beta fix; see the narrowing in §3 that costs no TLS verification.
- **`devdeck_http_send` not behind `guardRemote`.** The argument — it can only replay a saved request, so an agent never supplies a URL — is sound and now legible, which means the *tripwire* is legible too. An attacker reading `mcptools.ts:410-422` knows exactly which future edit turns an agent's shell into an SSRF primitive. The tripwire should be a test, not a comment (F-5).
- **`aikeys.status()` / `gitpat.status()` reporting "nothing configured" when the store is unreadable.** Was: the author sees a wrong label on his own machine and knows better. Now: a stranger with a damaged store is told nothing is configured, re-types the key, and the save path is the same family that once deleted every stored key from a damaged `aikeys.json`. **Re-price up** — this is one corrupted file away from being a data-loss report from a beta user.
- **The remote `fs:write` force-write.** Was: the author overwrites his own edit. Now: a lost write between a stranger's phone and an agent in a pane, over a stranger's employer's code, with no mtime and therefore no way to notice.

And one obligation publication *created*: `tests/publishedIdentifiers.test.ts` protects **the author's** identifiers in **tracked files**. Nothing protects **a user's** identifiers in **a diagnostics paste** — and the first thing a stranger does when a pane dies is paste diagnostics into a public issue tracker. That is F-3.

## 2. What a beta user's machine adds

**A corporate proxy.** `netproxy.ts` sets `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`/`NODE_EXTRA_CA_CERTS` into `process.env` so every spawned pty and child inherits them. That is the right fix for the pain it targets (npm/git/gh). Two things it does not do, and one claim in its own header that does not hold:

- `undici`'s `fetch` — which is *every* path in `http.ts`: the API panel, the phone relay, the MCP replay — **does not read proxy environment variables.** Behind a mandatory proxy, terminals work and the whole HTTP surface fails with a bare `fetch failed`.
- `NODE_EXTRA_CA_CERTS` is read **once, at process start**. Setting it from an IPC handler cannot affect the main process's own TLS, only children spawned afterwards.
- The header comment says "the main process's own TLS/fetch was fixed at startup." `grep -rn netproxy src/` finds `applyProxy` called from exactly one place — `index.ts:637`, the `netproxy:apply` IPC handler — and nothing at startup. **That claim is not backed by code.** It should be deleted or made true.

Not a hole. But it means the phone feature and the API panel are dead on a managed LAN and the error says nothing. Cheapest fix: install undici's `EnvHttpProxyAgent` as the global dispatcher when a proxy is configured, and tell the user in the UI that the CA path takes effect after a restart.

**Antivirus that kills PowerShell.** Understood already (`pty-fastfail-avast`). The boundary-relevant part is that `exitNotice` is computed host-side and sent to the phone — correct, since the phone cannot know the host OS. What is unproven is that it fires for the AV exit code on a machine that is not this one.

**A different shell.** `defaultShell()` is `powershell.exe -NoLogo` unconditionally on Windows. In a managed estate where PowerShell is blocked by policy, every pane dies at spawn. `cwdNotice` handles a bad cwd; the missing-shell branch handles a missing shell; a *policy-blocked* shell is a third state that will read as one of the other two. A first-run cliff, not a boundary.

**`safeStorage` unavailable.** `devices.ts`, `aikeys.ts` and `gitpat.ts` all fall through to `"b64:" + base64` when `safeStorage.isEncryptionAvailable()` is false. That is not encryption, it is an encoding, and on this machine it never happens. On five others it might (a machine without a DPAPI-backed profile, a roaming profile, some VDI setups). There is no UI anywhere that says "your pairing token and API keys are stored unencrypted on this machine." Same family as the `aikeys.status()` lie and now with a stranger on the other end.

**Someone else on their LAN.** That is §3, and it is the one that matters.

## 3. The phone pairing and the remote server

This is the only surface that leaves the machine, it has never rendered on real hardware, and it has never been attacked from a foreign network. What follows is ranked in the Findings section; here are the two structural observations that are not individual bugs.

**Nothing re-checks the network after the bind.** `chooseBind("lan")` correctly returns `0.0.0.0` — the user asked for the LAN, and refusing would be the inverted-request bug the function exists to prevent. `boundHost` is honest about the interface it actually took, and the panel can say so. But the bind happens **once**, in `start()`, and the app never notices that the machine moved. A beta user starts the remote server at home, closes the lid, and opens it at a co-working space: the server is still listening on every interface, with a live pairing token, on a network full of strangers. Every guard behaves exactly as designed and the exposure is completely different. **Recommendation: tear the server down on a network-interface change and on resume, and require an explicit restart.** Cheap, and no product seat will ask for it.

**The DNS-rebinding narrowing that costs nothing.** The declined fix was "connect by address and carry `Host`", rejected because it breaks TLS SNI/verification for ordinary requests. That objection applies only to `https:`. Every interesting rebind target — an MCP server on 8787, a router admin page, `169.254.169.254` — is plain `http:`, where there is no certificate to verify and no SNI to get wrong. **Pin the resolved address for `http:` targets only; leave `https:` on name resolution.** That halves the exposure at zero TLS cost and answers the objection the handoff correctly insists must be answered. A spike, not a pre-beta fix.

Two things I looked at and would **not** touch:

- `case "attach"` taking any `termId` the client sends. The comment is right: `case "input"` already writes arbitrary bytes to an arbitrary pty, so pairing *is* the trust boundary and the attach check buys tap-addressing hygiene, not security. Do not "harden" it; the honesty of that comment is worth more than the check.
- `originOk` returning `true` for a missing `Origin`. Correct — a browser always sends it on a WS handshake, so absence means a non-browser client, which is not the thing being guarded.

## 5. What the roadmap is missing on security grounds

**D1's security value is in `db.ts`, not in `DbPanel`.** D1 is authorised as deleting three panels, their IPC handlers and channels, and four production deps — but `devdeck_db_query` was judged to pass the agent-edge test on its own merits, and the remote `db:conns`/`db:tables`/`db:query` handlers are "partly in question." If those survive, `db.ts` survives, and so does all of this:

- `buildPgConfig`: `ssl: p.ssl ? { rejectUnauthorized: false } : undefined` (`db.ts:176`)
- `buildMyConfig`: the same (`db.ts:188`)
- `buildMssqlConfig`: `options: { encrypt: !!p.ssl, trustServerCertificate: true }` — **unconditionally**, in both the pool builder (`db.ts:204`) and `testConnection` (`db.ts:400`)

So the "SSL" checkbox in the UI delivers *encrypted* and not *authenticated*, on all three network drivers, against any MITM on the path. On this machine, talking to `localhost`, that is nothing. On a beta user's machine on a foreign network, reaching a remote database, it is a security control that lies to the user — the same class as the four "Copied" messages. Keeping `devdeck_db_query` also keeps the unproven pg `WITH … AS (DELETE …)` claim, keeps `mssql`'s outright refusal as a permanent user-visible dead end, and keeps four packages in the supply chain of a repo anyone can now read.

**The security recommendation: execute D1 as a `db.ts` deletion, not a panel deletion.** If `devdeck_db_query` must live, then those three TLS lines are a pre-beta fix and the pg CTE claim needs a live database before the beta, not after. Deleting is strictly cheaper than proving.

Three things not on the roadmap that belong there:

- **No dependency/CVE gate.** Public repo, nine production deps including a native pty and `ws`, and CI does not run `npm audit`. It is the cheapest security item available and nobody has asked for it.
- **No `SECURITY.md` and no disclosure path.** Someone who reads `guards.ts` and finds F-1 has exactly one way to report it: a public issue on a public repo, where it is a live 0-day against five users the moment it is filed.
- **`devdeck-archive-private` has no tripwire.** The rule "never make it public" is currently a fact somebody remembers. `tests/gitIdentity.test.ts` and `tests/publishedIdentifiers.test.ts` exist because a remembered rule failed twice in one week. A check that fails if that repo's visibility is not `private` costs one `gh` call.

**Does anything block?** Not on its own — *provided* items 1–3 land and the remote server ships **off by default, with pairing behind an explicit opt-in and a one-line statement of what the current bind exposes**. If the beta ships with the phone server enabled, or with F-1 open, then **F-1 blocks the beta**: it is a proven, remotely-reachable SSRF from a device on a network the author does not control, and the source that explains why the guard was thought to work is now readable by the person attacking it.

## Findings

Ranked by reachability.

### F-1 — `isBlockedAddress` enumerates one IPv4-in-IPv6 embedding and allows the rest

- **Entry point:** paired phone → WebSocket `{ t: "http", req }` (`src/main/server.ts:551`) → `httpSend(req, { guardRemote: true })`.
- **Decision point:** `src/main/guards.ts:47-49` — the `::ffff:/96` branch of `isBlockedAddress`, and the bare `return false` at `guards.ts:54`.
- **Exact inputs (all proven to reach `fetch`):**
  - `http://[64:ff9b::a9fe:a9fe]/latest/meta-data/` — NAT64 well-known prefix (RFC 6052) carrying `169.254.169.254`
  - `http://[2002:7f00:1::]:8787/mcp` — 6to4 (RFC 3056) carrying `127.0.0.1`
  - `http://[::7f00:1]:8787/mcp` — IPv4-compatible (RFC 4291 §2.5.5.1) carrying `127.0.0.1`
  - `http://[::ffff:0:7f00:1]:8787/mcp` — IPv4-translated (RFC 2765) carrying `127.0.0.1`
  - `http://[2001:0:0:0:0:0:3f57:fffe]/` — Teredo (RFC 4380), inverted, carrying `192.168.0.1`
  - `http://rebind.example.com/` where the attacker's zone answers `AAAA 64:ff9b::c0a8:1`
  - a `302 Location: http://[64:ff9b::7f00:1]:8787/mcp` from any allowed public host
- **What it reaches:** whatever the embedded IPv4 address reaches. On this machine that includes DevDeck's own MCP server on `127.0.0.1:8787` (bearer-token protected, so a read of `/mcp` is refused — but it is a port scan and a reachability oracle inside loopback), the cloud metadata address on any VM, and the whole of RFC 1918.
- **Why the second layer does not save it:** `blockedTarget` (`src/main/http.ts:70`) re-checks the *resolved* address, and `dns.lookup` returns a numeric host verbatim. Confirmed on this machine:
  ```
  "64:ff9b::7f00:1" -> [{"address":"64:ff9b::7f00:1","family":6}]
  "::7f00:1"        -> [{"address":"::7f00:1","family":6}]
  "2002:7f00:1::"   -> [{"address":"2002:7f00:1::","family":6}]
  ```
  Both layers ask the same wrong question and get the same wrong answer. Contrast `localhost.` and `127.0.0.1.`, which the *text* guard also misses but which the resolver layer catches (`localhost.` resolves to `::1` + `127.0.0.1`) — there defence in depth works, and that is the difference between a weakness and a hole.
- **Also missing, same function, same reason:** `fec0::/10` (deprecated site-local) and `ff00::/8` (multicast). `tests/server-guards.test.ts:82` currently **asserts `fec0::1` is allowed**, with the comment `// outside the /10`. The intent was to pin the `fe80::/10` boundary; the effect is a test asserting a bypass. Fixing F-1 requires changing that line, and it must be changed rather than the guard widened to keep it green.

### F-2 — `/xterm.js` is an unauthenticated 488 KB synchronous disk read

- **Entry point:** anyone who can open a TCP socket to the remote server's port. No token, no cookie, no device record.
- **Decision point:** `src/main/server.ts:320-329` — the two static-asset branches sit **above** `const { auth, token } = authFor(req, url, true)` at `server.ts:331`. `xtermAsset` (`server.ts:107`) does `require.resolve` + `readFileSync(…, "utf8")` on every call; nothing is cached.
- **Measured on this machine, warm page cache:** 200 calls in 689.8 ms = **3.45 ms per request**, 488,663 bytes each. **290 requests/second saturates the event loop.**
- **What it reaches:** the Electron main process's single thread — which relays every PTY byte to every pane, answers every `fs:*`/`db:*`/`git:*` IPC call, and runs `authenticate()`. The failure throttle in `devices.ts` was added *precisely* because `authenticate()` was "attacker-paced, on the same thread that drives the UI and relays every PTY." This path is attacker-paced, on the same thread, an order of magnitude more expensive per request, and **in front of the throttle**.
- **Why it is not "just a DoS":** `devices.ts` explicitly refuses to answer a bad token by blocking, "so delaying a response by blocking would hand an attacker the very stall the throttle exists to prevent." This hands them the stall through the front door.

### F-3 — the diagnostics record publishes the user's home path, and there is no rule that folds it

- **Entry point:** a beta user hits a problem, copies diagnostics (clipboard-only, by design), pastes it into a public issue.
- **Decision point:** `src/main/redact.ts`'s `RULES` array (`redact.ts:79-228`). It is thorough on credentials — PEM blocks, `sk-ant-`, `sk-proj-`, `[sr]k_live`, `gh[pousr]_`, `github_pat_`, `npm_`, `AKIA`/`ASIA`, `AIza`, `xox[abposr]-`, JWTs, URL userinfo, `Bearer`/`Basic`/`Token`, and both the `=` and `:` name-keyed rules. **There is no rule for a filesystem path, a home directory, an OS username, or a hostname.**
- **What is in the record:** `shell.resolved` and `shell.customPath` (`diagnostics.ts:290-296`) and every `agents[].command` (`diagnostics.ts:169`) are file paths, redacted for *credentials* and otherwise verbatim. On Windows an agent CLI path is routinely `C:\Users\<real name>\AppData\...`, and a custom shell or an agent command can carry a client or employer directory name.
- **Why this seat cares more than it looks:** the repo spent this week rewriting history twice to remove exactly this class of identifier, and built two tests to stop it recurring. Both of them scan *tracked files* for *the author's* tokens. The moment there are users, the same leak reopens one level out — a stranger's identifier, in a paste, in a public issue — and neither guard looks there.
- **Fix:** one rule in `redact.ts`, at the same layer as the rest, folding `os.homedir()` and the generic `\Users\<seg>\` / `/home/<seg>/` / `/Users/<seg>/` shapes to `%USERPROFILE%` / `~`. Keep the tail of the path: "the agent resolved to `%USERPROFILE%\AppData\Local\…\claude.exe`" is the fact a reader needs, and the username is not part of it.

### F-4 — the bind is decided once and never re-examined

- **Entry point:** the machine moves. A lid closes at home and opens on a network the author, and the user, do not control.
- **Decision point:** `src/main/server.ts:206-216` — `localAddresses()` and `chooseBind()` run once inside `start()`; `boundHost` is set at `server.ts:713` and only cleared by `stop()`. Nothing listens for an interface change.
- **What it reaches:** with `bind: "lan"` the server is on `0.0.0.0` with a live pairing token. Every guard is behaving correctly and the exposure is a different network.
- **Not exploited** — this is reasoned from the code, and it needs the app plus two networks to demonstrate. It is here because it is the highest-value control that does not exist rather than the highest-value bug that does.

### F-5 — `devdeck_http_send`'s safety is a comment, not a test

- **Entry point:** an agent in a pane, via MCP, today: none — `mcptools.ts:409-418` refuses anything but a saved-request id and never accepts a URL.
- **Decision point:** `src/main/mcptools.ts:413-419`.
- **Why it is a finding anyway:** the whole argument is "the agent never supplies a URL." Nothing enforces that but the current shape of the `switch`, and `deps.httpSend` is wired to the **unguarded** `httpSend` (no `guardRemote`). The first edit that adds a `url` argument turns an agent's shell into a full SSRF primitive against loopback with no guard in the path at all, and that edit will look harmless in review. Make the tripwire executable.

## The exploit

All of the following was run. `tests/http-ssrf.test.ts` already has the dns-mock + fetch-stub harness this needs; the only change is that the mock must return a numeric host verbatim, the way real `getaddrinfo` does.

### In `tests/http-ssrf.test.ts` — the boundary

Add to the mock at the top of the file (this is the honest half: without it the test cannot reproduce what the resolver actually does with a literal):

```ts
vi.mock("dns/promises", () => ({
    lookup: async (host: string) => {
        // Real getaddrinfo hands a numeric host straight back - verified on
        // Windows for 64:ff9b::7f00:1, ::7f00:1 and 2002:7f00:1::. Without
        // this the suite cannot see that both layers of the guard ask the
        // same question of a literal and get the same answer.
        if (host.includes(":") && /^[0-9a-f:]+$/i.test(host)) {
            return [{ address: host, family: 6 }]
        }
        const addrs = dnsMock.map.get(host)
        if (!addrs) throw new Error(`ENOTFOUND ${host}`)
        return addrs.map((address) => ({ address, family: address.includes(":") ? 6 : 4 }))
    }
}))
```

```ts
describe("relayed HTTP - IPv4 wearing a hat other than ::ffff:", () => {
    const cases: [string, string][] = [
        ["NAT64 well-known prefix -> the cloud metadata address", "http://[64:ff9b::a9fe:a9fe]/latest/meta-data/"],
        ["6to4 -> loopback", "http://[2002:7f00:1::]:8787/mcp"],
        ["IPv4-compatible -> loopback", "http://[::7f00:1]:8787/mcp"],
        ["IPv4-translated -> loopback", "http://[::ffff:0:7f00:1]:8787/mcp"],
        ["Teredo -> 192.168.0.1", "http://[2001:0:0:0:0:0:3f57:fffe]/"]
    ]
    for (const [why, url] of cases) {
        it(`refuses ${why}`, async () => {
            const calls = stubFetch({})
            const res = await httpSend({ method: "GET", url }, { guardRemote: true })
            expect(res.error).toBe(BLOCKED)
            expect(calls).toEqual([])
        })
    }

    it("refuses a hostname whose AAAA record is a NAT64-mapped private address", async () => {
        dnsMock.map.set("rebind.example.com", ["64:ff9b::c0a8:1"])
        const calls = stubFetch({})
        const res = await httpSend({ method: "GET", url: "http://rebind.example.com/" }, { guardRemote: true })
        expect(res.error).toBe(BLOCKED)
        expect(calls).toEqual([])
    })

    it("refuses a redirect hop into a NAT64-mapped loopback", async () => {
        dnsMock.map.set("api.example.com", ["93.184.216.34"])
        const calls = stubFetch({
            "https://api.example.com/": { status: 302, location: "http://[64:ff9b::7f00:1]:8787/mcp" }
        })
        const res = await httpSend({ method: "GET", url: "https://api.example.com/" }, { guardRemote: true })
        expect(res.error).toBe(BLOCKED)
        expect(calls.map((c) => c.url)).toEqual(["https://api.example.com/"])
    })
})
```

**Observed against `src/main/guards.ts` as it stands: 7 of 7 fail.** Every one of them returned `{ ok: true, body: "REACHED" }` with the stubbed `fetch` recording the call — the guard did not merely mis-judge the address, it never refused the request. Against the patched guard below: 7 of 7 pass, and a control case (`https://api.example.com/x` resolving to `93.184.216.34`) still succeeds.

### In `tests/server-guards.test.ts` — the unit battery

```ts
describe("isBlockedAddress: every embedding of an IPv4 address, not just ::ffff:", () => {
    // The bug this pins is not "::ffff: was wrong" - that was fixed. It is that
    // ::ffff: was the only embedding ENUMERATED, and a bare `return false`
    // answered for all the others. One instance of a class is not the class.
    const embedded: [string, string][] = [
        ["::7f00:1", "IPv4-compatible, RFC 4291 2.5.5.1"],
        ["::127.0.0.1", "IPv4-compatible, dotted"],
        ["::ffff:0:7f00:1", "IPv4-translated, RFC 2765"],
        ["64:ff9b::7f00:1", "NAT64 well-known prefix, RFC 6052"],
        ["64:ff9b::a00:1", "NAT64 -> 10.0.0.1"],
        ["64:ff9b::c0a8:1", "NAT64 -> 192.168.0.1"],
        ["64:ff9b::a9fe:a9fe", "NAT64 -> the cloud metadata address"],
        ["2002:7f00:1::", "6to4, RFC 3056"],
        ["2002:c0a8:1::1", "6to4 -> 192.168.0.1"],
        ["2001:0:0:0:0:0:3f57:fffe", "Teredo, RFC 4380, inverted"]
    ]
    for (const [addr, why] of embedded) {
        it(`blocks ${addr} (${why})`, () => expect(isBlockedAddress(addr)).toBe(true))
    }

    it("blocks the two IPv6 scopes that had no branch at all", () => {
        expect(isBlockedAddress("fec0::1")).toBe(true) // fec0::/10, deprecated site-local
        expect(isBlockedAddress("ff02::1")).toBe(true) // ff00::/8, multicast
    })

    it("still allows ordinary global IPv6", () => {
        expect(isBlockedAddress("2606:2800:220:1:248:1893:25c8:1946")).toBe(false)
        expect(isBlockedAddress("2606:4700::1111")).toBe(false)
        expect(isBlockedAddress("2001:4860:4860::8888")).toBe(false) // 2001: but not 2001:0::/32
    })
})

it("reads a trailing root dot as the name it is", () => {
    // The resolver layer catches `localhost.` (it resolves to ::1 + 127.0.0.1),
    // so this is defence in depth, not the boundary - but a text guard that
    // cannot see the most common FQDN spelling of the one name it hard-codes
    // is not doing its job.
    expect(isBlockedRemoteUrl("http://localhost./")).toBe(true)
    expect(isBlockedRemoteUrl("http://LOCALHOST./")).toBe(true)
```

## The fix

### F-1 — `src/main/guards.ts`, at the decision point

Replace the single `::ffff:/96` branch and the `::`/`::1` branches with one call, and add the two missing scopes:

```ts
    if (h.includes(":")) {
        const groups = parseIpv6(h)
        if (!groups) return true // an address we cannot read is not an address we allow
        // ::ffff:/96 was the ONE embedding this enumerated, and every other way
        // of writing an IPv4 address inside an IPv6 one answered "not local"
        // for 127.0.0.1 wearing a different hat. All of them are judged as the
        // IPv4 address they carry - see embeddedV4.
        const v4 = embeddedV4(groups)
        if (v4) return blockedV4(v4)
        if ((groups[0] & 0xffc0) === 0xfe80) return true // fe80::/10, link-local
        if ((groups[0] & 0xfe00) === 0xfc00) return true // fc00::/7, unique-local
        if ((groups[0] & 0xffc0) === 0xfec0) return true // fec0::/10, deprecated site-local
        if ((groups[0] & 0xff00) === 0xff00) return true // ff00::/8, multicast
        return false
    }
```

```ts
/**
 * The IPv4 address an IPv6 address carries, as four octets, or null if it
 * carries none.
 *
 * "Is this loopback?" is a question about where the packet lands, and several
 * prefixes exist whose entire purpose is to carry an IPv4 destination inside
 * an IPv6 literal. Enumerating one of them and returning "allowed" for the
 * rest is the `[::ffff:7f00:1]` bug in five more spellings - and a resolver
 * hands these back verbatim, so the second layer of the guard asks the same
 * question and gets the same wrong answer.
 */
function embeddedV4(g: number[]): number[] | null {
    const split = (hi: number, lo: number): number[] => [hi >> 8, hi & 0xff, lo >> 8, lo & 0xff]
    const zeros = (from: number, to: number): boolean => g.slice(from, to).every((x) => x === 0)
    // ::ffff:0:0/96 IPv4-mapped, and ::/96 IPv4-compatible (RFC 4291 2.5.5.1,
    // deprecated but still parsed, and still resolvable as a literal). `::`
    // and `::1` fall out of this as 0.0.0.0 and 0.0.0.1, both already blocked
    // by blockedV4's `a === 0`, so they need no separate branch any more.
    if (zeros(0, 5) && (g[5] === 0xffff || g[5] === 0)) return split(g[6], g[7])
    // ::ffff:0:0:0/96 IPv4-translated (RFC 2765 SIIT).
    if (zeros(0, 4) && g[4] === 0xffff && g[5] === 0) return split(g[6], g[7])
    // 64:ff9b::/96 NAT64 well-known prefix (RFC 6052).
    if (g[0] === 0x0064 && g[1] === 0xff9b && zeros(2, 6)) return split(g[6], g[7])
    // 2002::/16 6to4 (RFC 3056) - the v4 address is the next 32 bits.
    if (g[0] === 0x2002) return split(g[1], g[2])
    // 2001:0::/32 Teredo (RFC 4380) - the v4 server address is the last 32
    // bits, stored bitwise-inverted.
    if (g[0] === 0x2001 && g[1] === 0) return split(~g[6] & 0xffff, ~g[7] & 0xffff)
    return null
}
```

And one line in `isBlockedRemoteUrl`, for the text layer:

```ts
        // A single trailing dot is the DNS root, not part of the name:
        // `localhost.` resolves to 127.0.0.1 on every stack and, read as text,
        // was neither "localhost" nor a dotted quad.
        const h = u.hostname.toLowerCase().replace(/^\[|\]$/g, "").replace(/\.$/, "")
```

Note the deliberate non-changes. `100.64.0.0/10` stays allowed — that is a decision, documented, and blocking it breaks the tailnet bind this feature exists for. `blockedV4`'s six IPv4 ranges are untouched, because I could not build an exploit for the multicast/reserved ones and I am not going to widen a guard on a hunch.

### F-2 — `src/main/server.ts`, at the read

```ts
/**
 * The two static assets, read once per process rather than once per request.
 *
 * This path is served BEFORE authFor and before the failure throttle in
 * devices.ts, so it was 488 KB of synchronous readFileSync available to
 * anyone who could open a socket - 3.45 ms of blocked event loop per
 * request, measured, on the same thread that relays every PTY byte. The
 * throttle next to `authenticate` exists because that call was
 * "attacker-paced, on the same thread that drives the UI"; this one was
 * worse and in front of it. The cache is per-process because the files are
 * inside the app bundle and cannot change while it runs.
 */
const xtermCache = new Map<string, string>()
function xtermAsset(file: "xterm.js" | "xterm.css"): string {
    const hit = xtermCache.get(file)
    if (hit !== undefined) return hit
    const main = require.resolve("@xterm/xterm")
    const pkgDir = dirname(dirname(main))
    const path = file === "xterm.js" ? join(pkgDir, "lib", "xterm.js") : join(pkgDir, "css", "xterm.css")
    const body = readFileSync(path, "utf8")
    xtermCache.set(file, body)
    return body
}
```

That removes the disk read. It does **not** remove the response write, so a flood still costs bandwidth and a string copy — which is what a normal HTTP server costs, and is the right place to stop. If more is wanted, add `Cache-Control: public, max-age=31536000, immutable` and answer a matching `If-None-Match` with 304, so a real client fetches each asset once.

### F-3 — `src/main/redact.ts`, one rule in `RULES`

```ts
    // A home directory is an identifier. `shell.resolved`, `shell.customPath`
    // and every `agents[].command` in the diagnostics record are file paths,
    // and on Windows an agent CLI lives under C:\Users\<the user's name>. The
```

## What I could not prove

Mandatory section, and it is the longest one here for a reason.

- **F9 — does `new Notification(...)` survive `setPermissionCheckHandler(() => false)` on a `file://` renderer?** Still open, and I did not settle it. What I established: `notifications` is in the permission list `setPermissionCheckHandler` is documented to receive (`node_modules/electron/electron.d.ts:13352`), and `setPermissionRequestHandler`'s list too (`:13361`) — so both the query and the request are denied. And `notifyAttention` (`src/renderer/src/store.ts:944-957`) **does not read `Notification.permission` at all**; it constructs and relies on `try/catch`, which per the Notification spec is the one thing that does *not* fire when permission is denied — the constructor succeeds, an `error` event is dispatched on the object, and nothing is shown. So the strong inference is that the "Desktop notifications" setting is a switch that does nothing, silently, in exactly the shape of the four lying "Copied" messages. **That is an inference, not an observation.** What settles it is one line over CDP against the running app: `Notification.permission` in the renderer, and then flipping the setting on and watching for a toast. If it reads `"denied"`, the fix is not a permission handler exemption — it is to send the notification from **main** (`new Notification()` from the `electron` module, which is not subject to renderer permissions) over IPC, and to make the settings toggle reflect what actually works. **This is the one claim I would settle first**, because it is a one-line observation gating a shipped, advertised, user-facing security-adjacent honesty bug on five machines.
- **The pg `WITH x AS (DELETE …) SELECT` bypass has still never been watched to fail.** Docker Desktop is not running on this machine (`open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file specified`), so I could not stand up a Postgres. I did not settle it by reading either, and I will not restate the mechanism as proof. What I would run: `docker run --rm -e POSTGRES_PASSWORD=probe -p 55432:5432 postgres:16`, seed a table, then call `runQuery(profileId, "WITH x AS (DELETE FROM t RETURNING *) SELECT * FROM x", { readOnly: true })` through `db.ts` and assert both that it errors *and* that the row count is unchanged afterwards — the second assertion is the one that matters, because an error with the delete already committed is the failure mode. Same script should cover `SELECT 1; DROP TABLE t` (to confirm `rows: PG_PAGE_ROWS` really is holding the extended protocol) and `CREATE TEMP TABLE`. Until then: **only sqlite is proven end-to-end.**
- **`mysql2`'s `localInfile` default.** A malicious MySQL server can ask a client for an arbitrary local file, and `buildMyConfig` does not set `localInfile`. I could not locate the option's default in the installed package (`mysql2`'s `exports` map blocks requiring `lib/connection_config.js`, and a grep of its `lib/*.js` for the identifier found nothing where I looked). **Unverified in both directions** — I am not claiming a hole and not claiming safety. If `db.ts` survives D1, set `localInfile: false` explicitly, because an explicit `false` costs one line and removes the question.
- **Reach for IPv4 multicast, `240.0.0.0/4` and `255.255.255.255`.** `blockedV4` allows all of them. I could not build an exploit: an HTTP request is TCP, and TCP does not establish to a multicast or broadcast address. I left them out of the fix and out of the pre-beta list rather than widening the guard for a shape I could not demonstrate.
- **Actual routability of `::7f00:1` and `2002:7f00:1::` on Windows 11.** The *guard decision* is proven wrong for both — that is the finding, and it stands regardless. Whether a packet to an IPv4-compatible address reaches loopback on a current Windows stack, and whether 6to4 is enabled on any given beta machine, I did not test. NAT64 is the one where I would put the money: every IPv6-only mobile network runs it, and it is a plain `/96` translation. The honest caveat on the fix is that a **site-specific** NAT64 prefix is not enumerable at all — only the well-known `64:ff9b::/96` is — which is another argument for the http-only address pinning in §3.
- **F-2 was measured out-of-process, not against the running server.** 3.45 ms/call is `require.resolve` + `readFileSync` + utf8 decode of the real 488,663-byte file in a bare `node -e`, repeated 200 times warm. The per-request cost and the code path (asset branches above `authFor` at `server.ts:320` vs `:331`) are both certain; the *observed* freeze is not.

Any of it.** The decision card has still never rendered on real hardware, the pairing flow has never been walked on a phone, and no part of the remote server has been attacked from a foreign network. Every claim in §3 is derived from the code. The `dvh` fix, the header-overflow fix and the terminal-overflow clip are all still review-only.

## F9 — settled by measurement, 2026-09-10

Open since before 0.11.1 and listed in `HANDOFF.md` §4 as an unproven claim that
must not be restated as verified. It is now verified, and the inference above was
correct in every part. Measured on a real `file://` renderer, scratch profile,
one CDP session (`scratchpad/f9-notification.js`):

| probe | result |
|---|---|
| `typeof Notification` | `function` |
| `Notification.permission` | **`denied`** |
| `new Notification(...)` | **did not throw**; returned an `object` |
| `Notification.requestPermission()` | resolved **`denied`** (no prompt) |
| control: `navigator.clipboard.writeText` | blocked, `NotAllowedError` |

The control matters: it proves the handler is active and *not* selective, so
notifications are denied by the same mechanism that already denies the clipboard.

**Consequence.** `setPermissionCheckHandler(() => false)` denies notifications,
and Chromium's response to a denied notification is to construct the object and
silently drop it. `notifyAttention` (`store.ts:944`) constructs and trusts
`try/catch` — the one signal that does *not* fire here. So the Desktop
notifications toggle in Settings has never worked, produces no error, and writes
nothing anywhere. A user who enables it is told the app will tell them which
agent needs them; the app then does not, and nothing reports the failure.

This is worse than the display lies already accepted in §4 (`aikeys.status()`,
`gitpat.status()`): those misreport a state, this one silently discards the
product's headline function on the surface a user reaches for when they stop
watching the deck.

**The fix is the one named above** — notify from main over IPC, where the
permission handler does not apply — **not** to exempt `notifications` from the
handler, which would re-open the surface the handler exists to close. Whatever
lands, the toggle must not be able to be on while nothing is delivered: if the
capability is unavailable, the setting has to say so.
