## What DevDeck already has (the bundle, scattered)

- **Launcher.** `settings.ts` presets are flat strings: `command`, `resumeArgs`,
  `apiKeyEnv`/`modelEnv`, a `badge`. Six seeded presets (Claude, Claude Opus,
  Claude bypass, Codex, Gemini, plus two build/test shells). `isUnsafeAgent()`
  (`settings.ts:262`) flags a command line, matched on the string itself so a
  hand-edited preset is caught the same as the bundled bypass one — no policy
  engine, a regex and a badge.
- **Env at spawn.** `mcpserver.hookEnv(sessionId, isAgent)` (`mcpserver.ts:327`)
  already computes `DEVDECK_SESSION`, `DEVDECK_HOOK_URL`, and
  `DEVDECK_MCP_TOKEN` (agent panes only) and `index.ts:574` injects them into
  every pty DevDeck spawns. The values `attention-hooks.md` asks a user to
  hand-copy are values DevDeck is already computing for that exact pane.
- **Skills/subagents.** `ExtendAgentModal.tsx` + `skills.ts`: clone-preview-copy
  into `.claude/skills` or `.claude/agents`, project or global scope, one
  curated catalog entry ("Animation & interface-design skills"). Confirmed
  genuinely used once: `.gitignore:27-28` excludes exactly
  `.claude/skills/apple-design/` and `.claude/skills/animation-vocabulary/` —
  the two names inside that one catalog entry — and no other path in the repo
  shows this pattern. The 2026-07-14 spec's own non-goals: *"No hooks or
  slash-commands. No non-Claude (.codex, Gemini) formats. No marketplace
  backend… No auto-update."* The MCP tab was deferred at ship and never built.
  One real use, zero uses for the panels D1 deleted. **This brief's framing —
  keep it exactly as is, grow it not at all — is upheld below, not overturned.**
- **MCP server.** `mcpserver.ts`: loopback HTTP on `127.0.0.1:8787`, one
  bearer token, `TOOLS` down to two (`devdeck_projects`,
  `devdeck_console_logs`) after five were retired with the deleted panels —
  and a retired call answers with what happened to the tool, not `Unknown
  tool`, so an agent's own `CLAUDE.md` reference doesn't read as a broken
  server. `.mcp.json` write (`mcp.ts:writeMcp`) is the load-bearing precedent
  for the ruling below: it reads the existing file, **preserves every other
  top-level key**, refuses to write at all if the file exists but can't be
  parsed (never clobbers on a read failure it can't reason about), and writes
  atomically. DevDeck already merge-writes into a Claude Code project config
  file, safely, today.
- **Worktrees.** `worktrees.ts`: git worktree-per-agent, sibling
  `<repo>.worktrees/` folder, opt-in since 0.13.0 (default off). App-managed
  worktree *lifecycle* as the unit of navigation was already killed twice
  (`IDEAS.md` 2026-08-30, reaffirmed 2026-09-10) for retiring "a project is
  the unit of context" — DevDeck already refused to own this axis of the
  harness.
- **Hooks.** `docs/attention-hooks.md`, shipped `b7e2d69`: Claude Code
  `Notification`/`Stop`/`UserPromptSubmit`/`SessionStart` as `http` hooks
  posting to the same MCP server. Live in 0.14.0. The gap named in the brief
  is real and specific: the user hand-writes JSON into
  `.claude/settings.local.json`, and the doc itself flags the trap —
  `allowedEnvVars` omitted means Claude Code silently substitutes an **empty
  string** for the token, producing "a hook that fires and does nothing," with
  no DevDeck-visible error.

## Who actually manages a harness as one object

Nobody does, fully — that is itself a finding. **Pane** owns worktree
lifecycle, agent-agnostic. **Orca** owns a skills/plugin marketplace with a
published threat model. **Herdr** owns cross-CLI, now cross-machine, breadth.
Each competitor consolidated *one* axis of the bundle (launch, worktree,
extensibility, hooks) into a first-class object and left the rest to the
underlying CLI's own config files. None of them ships a unified "harness"
editor spanning launch + env + worktree + hooks + skills + MCP + permission
posture as one persisted record. The category term in the brief is useful for
*naming the bundle to reason about it*; it is not evidence a product exists
that manages it as one thing, and DevDeck building that unified object would
be a genuine first — which is a reason for suspicion, not ambition, given the
subtraction history below.

## Verdict

**Harness management as a general product category is not DevDeck's
business.** A persisted, editable "harness" object spanning presets, env,
worktrees, hooks, skills and MCP servers is a governance layer with no single
source of truth to derive it from — it would have to become one, which means
DevDeck starts *owning* copies of state that already lives correctly in
`settings.ts`, `.mcp.json`, `.claude/settings.local.json` and git's own
worktree metadata, and then must keep all of them in sync or lie. That is the
shape of the eleven-surfaces mistake this product spent a month unwinding, one
layer up: not eleven answers to "who needs me," but one new answer to "what is
this agent's setup," second-guessing files DevDeck does not own. It also costs
what D1 bought — `ROADMAP.md`'s forbidden list already refuses a fifth deck
key and a second dashboard "under any name, for any stack, however well
argued." The single most valuable thing to build next is **nothing on this
axis** — finish getting five strangers through the door with what already
shipped. The single thing to stop carrying, if anything, is the temptation
this brief itself represents: naming a category invites building toward it.

**On writing the hook config: yes, DevDeck should, later — and the reasoning
for "yes" doubles as the reasoning for "not yet."** Argued both ways:

*For.* DevDeck already does the structurally identical thing safely
(`writeMcp`: preserve-other-keys, refuse-on-unreadable, atomic). It knows
every value exactly — `current.token` and `config.port` from `mcpserver.ts`,
the project path from the project record, and which CLI a preset launches
from `settings.ts`'s `command` string — nothing here is inferred. And the
manual step it would retire is not merely inconvenient, it is the exact
failure class this product has spent a release fixing: a config gap that
**fails silently** (empty token, hook fires and does nothing) with DevDeck
showing no error, quietly falling back to the same screen-guessing Q1 exists
to replace. A feature that only works if hand-typed JSON is correct, with no
check that it is, is a documented trap wearing a doc as its only mitigation.

*Against.* `.claude/settings.local.json` is not DevDeck's file the way
`.mcp.json` is (DevDeck is the primary writer of its own MCP entry; it is a
guest in the hooks file). It's the user's **agent** trust config — hooks run
on every `Notification`/`Stop`/etc, gated by the CLI's own
`disableAllHooks`/`allowedHttpHookUrls`. The merge is structurally deeper than
`writeMcp`'s (per-event **arrays** of hook-entry objects, not a flat
`mcpServers` map — matching/dedup against a user's own unrelated hooks per
event, not just per top-level key), so a subtle bug has a wider blast radius:
a bad write can break the user's Claude Code entirely, outside DevDeck's own
window and with no DevDeck surface to report it from — the same silent-gap
failure mode, just authored by DevDeck instead of by the user.

Net: the precedent and the sourced facts make this buildable and safe *in
kind*; nothing about it is a guess. But it is still new engineering that
touches a file DevDeck does not own, and `ROADMAP.md`'s own "Behind those, in
order" list already says **"Neither Q1 nor Q2 is build-now, and neither may
precede a recorded session."** Completing Q1's rough edge is still Q1. Build
the read-only half now-adjacent (below), queue the writer.

## Build — ranked

1. **A read-only hook-config check, not a writer.** Given a project, report
   whether `.claude/settings.local.json` has DevDeck's four hook entries, with
   the right URL/port and `allowedEnvVars` present — surfaced as a line in the
   project's existing env/commands modal (no new modal; `LaunchOptions.tsx`'s
   surface already exists for exactly this class of fact). *Source of truth:*
   read the same file the doc tells the user to hand-edit, compared against
   the values `mcpserver.ts`/`hookEnv` already compute — nothing inferred.
   *Replaces:* the silent failure itself — today a broken hook produces no
   signal anywhere; this produces one, in the one place a user already looks
   before starting an agent. *Retires:* nothing yet, but is the precondition
   for retiring the manual step, and it is the cheap, reversible half. *Code
   paths:* a new read function beside `mcp.ts`'s reader, a line in the
   existing project modal. *Size:* small, read-only, no write-safety review
   needed. *If wrong:* it under- or over-reports a status the activity feed
   would also eventually reveal (a hook that fired unmatched is already
   logged there per the doc) — cheap to be wrong about, cheap to fix.
2. **The writer**, gated on evidence from (1) and from watching the beta (see
   below). *Source of truth:* identical to (1). *Replaces:* the copy-paste
   step in `attention-hooks.md` for Claude. *Retires:* the doc section itself,
   which becomes "DevDeck did this for you; here's what it wrote." *Code
   paths:* new module beside `mcp.ts`, reusing `atomicWrite`/`readJson`; must
   merge into existing per-event hook **arrays**, never replace them, and
   needs its own test class at the bar `skills.ts`'s `remove()` path-traversal
   fix set (a bug in this writer is a bug in someone else's tool). *Size:*
   medium — the merge logic is genuinely harder than `writeMcp`'s. *If wrong:*
   it corrupts a Claude Code config file outside DevDeck's own UI, with no
   DevDeck surface to catch it — argues for shipping (1) widely first and
   watching how often the manual step actually goes wrong before writing
   files for someone else's tool.
3. **Codex hook wiring (Q1-Codex).** Unchanged from the 09-10/09-15 rank:
   Codex hooks are stdin-command, not `http`, need a wrapper script, and are
   reported unreliable on Windows — queue behind W1 (does anyone run Codex).

## Killed

- **A unified "harness" object/panel spanning launch, env, worktree, hooks,
  skills, MCP and permission posture.** No single source of truth; would
  duplicate state DevDeck does not own; a new surface answering a question
  ("what is this agent's setup") nobody asked DevDeck to answer a second time.
  Matches the roadmap's forbidden "fifth deck key… under any name, for any
  stack, however well argued."
- **An MCP tab for `ExtendAgentModal`** (its own 2026-07-14 spec's deferred
  fast-follow). One catalog entry, one real use, zero pressure since. The
  brief's "keep exactly as is" stands; this would be growth with no user
  behind it.
- **Hooks/slash-command installation via `ExtendAgentModal`.** Explicit
  non-goal in its own spec, and now doubly wrong: Q1 delivers hooks by
  *posting to a server DevDeck runs*, not by installing files — a different
  mechanism entirely, so folding it into the skill-installer would conflate
  two unrelated systems under one UI.
- **A marketplace layer for skills/agents** (ratings, accounts, publishing,
  Orca's shape). Explicit non-goal in the 2026-07-14 spec; one real use is not
  evidence of demand for a storefront.
- **A visual permission-policy builder** replacing the raw `--dangerously-
  skip-permissions` flag string. `isUnsafeAgent()` plus the `BYPASS` badge
  already disclose this honestly, in form as well as color, per `DESIGN.md`'s
  own rule — there is nothing dishonest here to fix with a new UI.
- **App-managed worktree lifecycle as the harness's spatial/navigation unit**
  (Pane's mechanism). Killed twice already (`IDEAS.md` 08-30, 09-10) for
  retiring "a project is the unit of context." Reaffirmed; the market settling
  on it (trend-scan W5) is a watch item, not a reversal.
- **Widening the MCP bearer token beyond agent panes** so any terminal could
  reach the server for harness purposes. `attention-hooks.md` already refuses
  this by name — putting the token in every process's environment. Not ours
  to overturn; the doc's own reasoning holds.
- **Export/import a "harness bundle"** (presets + env + hooks) for moving
  setup between machines. Presets are already user-editable strings (killed
  as a breadth feature 2026-08-25); project `.claude/` files are already
  git-portable by design, and `settings.local.json` is gitignored on purpose
  because it's machine-specific. Solves a problem the filesystem already
  solves for anyone who dotfiles `.claude`. No demand signal; zero users so
  far.
- **A general "config doctor"** widened beyond hooks to also check `.mcp.json`
  drift, worktree state, proxy env, etc., as one health panel. Same shape as
  the forbidden fifth key — a second place to learn "is my setup right,"
  competing with the one place (the deck row) that already answers the
  adjacent question "is my agent waiting on me." Keep the doctor in build item
  1 scoped to exactly the hook gap named in this brief.
- **Fixing Claude Code's own `allowedEnvVars`-silently-empty footgun more
  generally** (e.g. warning on any hook, not just DevDeck's). Not DevDeck's
  surface — that's the vendor's own settings UI's job; DevDeck's doc already
  names the trap prominently for its own entry.

## Park

- **The writer (build item 2 above)**, until item 1 has run in at least one
  recorded session and either (a) shows candidates get the manual step wrong
  often enough to justify the wider blast radius, or (b) shows so few
  candidates even attempt Q1's setup that a writer would retire a step almost
  nobody takes.
- **Codex/Gemini halves of Q1** — condition: W1 (does a candidate run Codex or
  Gemini) fires with a real user, per the 09-10 ranking, unchanged.

## What the beta should watch for on this axis

Telemetry is forbidden, so all of this is observed-session evidence, per
`docs/beta/03-install-watch-protocol.md`:

1. **Does anyone reach the hooks doc at all, and if so, do they get it
   working?** The fourth asked fact (which tools a candidate already uses)
   tells `field` who is likely to try; watch whether they succeed
   unassisted, partially (SessionStart fires, Stop doesn't — the doc's own
   "wire fewer and DevDeck fills the gaps" case), or give up. This is the
   direct evidence for whether build item 2 (the writer) is worth its risk.
2. **The hooked-vs-screen disagreement count**, already recommended in the
   09-15 trend scan (`docs/beta/03-install-watch-protocol.md` addition) —
   reuse it rather than adding a second measurement; it's the same evidence
   this section needs.
3. **Does anyone open `ExtendAgentModal` at all**, and for what. A second real
   use, on a stranger's own initiative, is the only thing that would justify
   revisiting "keep it exactly as is, grow it not at all." Silence reaffirms
   it further.
4. **Does anyone ask why there's no single place to see "what is my agent's
   setup"** — the direct test of this document's core verdict. If nobody asks,
   the unified-harness idea was never a real gap. If several do, that's a
   finding for a future review, not license to build it on this evidence
   alone.

## Decide first

1. **Does the read-only hook checker (build item 1) count as "further
   engineering before step 9" and get barred by the same rule as Q1/Q2?**
   Default: **yes, it waits too.** It is small and safe, but the roadmap's
   rule is about what a stranger's first session needs, not about risk size —
   and a stranger's first session is not wrong without it, since the doc's
   troubleshooting section already covers the failure by hand. Build it
   immediately after step 9's first session, not before.
2. **If a candidate gets the hook wiring wrong in a recorded session, does
   `field` walk them through the fix live, or observe the failure
   unassisted?** Default: **observe first, then help** — the whole value of
   watch item 1 above is knowing whether the manual step survives contact
   with a stranger; helping too early destroys the only measurement that
   would justify building the writer.
