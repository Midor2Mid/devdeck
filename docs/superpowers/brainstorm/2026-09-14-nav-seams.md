# Nav seams — the worktree object and the merged search surface

`technical-director`, 2026-09-14. Ruling on the two shape-rather-than-surface
advantages taken from `.superpowers/market/D1-orca-layout.md`. Structure only:
what to build is `product-director`'s, the order is `pm`'s, the look is
`designer`'s (running in parallel, its own document).

---

## Verdict

**The merged search surface — fine once changed.** One condition: it is a
**finder**, not a second ranker of attention. It may not sort or badge by want.

**The worktree as a navigation object — fine once changed, and the change is
large.** Ship only the reversible half now (branch *visible*), and refuse the
irreversible half (branch *as grouping key*) until it can be built without
touching a persisted key.

**Both: correct idea, wrong month.** Neither passes the roadmap's second test —
*would a stranger's first session be wrong without this?* No. K6 fires
2026-09-22. Recorded as an objection, not as a block; the owner has decided.

---

## 1. The merged search surface — cost in seams: near zero

`ProjectSwitcher.tsx` (262 lines) and `CommandPalette.tsx` (270) already import
the same things that matter. Both call `useKeyStatus`. `CommandPalette` already
ranks sessions through `followRank` on the derived status. The merge is the
**union of two existing import sets** — no new IPC channel, no new store slice,
no cross-layer edge, nothing for `tests/architectureBoundaries.test.ts` to rule
on. This is the cheapest structural change on the table.

**The single-derivation pins already cover it, and this is why.** The scans in
`tests/signalSites.test.ts` are **directory-scoped, not file-listed**:
`rendererFiles()` globs `src/renderer/src/` recursively. A merged file is in
scope the day it exists for all three session invariants —
*builds every `status-` class from a derived value*, *ranks the follow order on
a derived status*, and *keeps `deckKeyStatus` to one caller* (which asserts
`callers.map(base)` equals exactly `["keyStatus.ts"]`). A merged palette that
re-derived "is there a process behind this tab" fails that assertion
automatically. **No new pin is warranted for the session-status half.**

### One new pin IS warranted, and it is the want

The three session pins are dir-scoped. The **want** pin is not: the
`wantKind(` assembly check reads only `store.ts`, via
`around("wantKind(", lines, 6, 22)`. `wantKinds` (`store.ts:1821`) is the one
predicate behind `wantsCount`, the taskbar badge and Ctrl+Shift+J. A merged
palette that wants to say "3 need you" or float them up the list is a **new
consumer of that fact from outside `store.ts`**, and nothing in the suite would
notice it re-deriving the answer as `keyStatusOf(s) === "attention"` — which is
not the same predicate: `wantKind` also weighs `awaited`, `lastAt`, `held`,
`exitCodeOf` and `seen`. A palette reading only the status would disagree with
the deck's own row about which sessions want you, in the surface a user opens
*because* the deck is ambiguous.

**Add to `tests/signalSites.test.ts`, same shape as the `deckKeyStatus` pin:**
a scan asserting that the only renderer file outside `tileState.ts` containing
a `wantKind(` call site is `store.ts`, plus the non-vacuous half (`tileState.ts`
really exports it; `store.ts` really calls it), exactly as the existing
one-caller pin does at `signalSites.test.ts:620`.

A surface that needs the want reads `wantKinds()` / `wantsCount` off the store.
It does not compute one.

### What the merge must reuse rather than re-derive

- `useKeyStatus` — never `s.status`, never `agentStatus[id]`.
- `wantKinds()` / `wantsCount` — never a status comparison.
- `projectSessionCounts` (`deck.ts`) for per-project counts, which already
  excludes dead and acknowledged sessions correctly.
- `orderByMru` / `previousProjectId` (`projectMru.ts`) for project ranking.
- `matches()` (CommandPalette's fuzzy subsequence) as the single matcher. Two
  match functions in one ranked list is how one query returns two orderings.

### The condition, and why it is structural

`ROADMAP.md` forbids, in terms, *"Answering 'which agent needs me' a second
time, in any form. No second list, panel, badge, tray window, pop-out or view
that re-answers the question the deck's one row already answers."* A palette
that **ranks sessions by want** is that second answer, arriving through the door
marked "no new surface". A palette that lets you **type a name and land on it**
is not. The line: the merged surface may *show* a session's derived status as a
row decoration; it may not *order* by attention and it may not carry a count.
That keeps the deck's row the only place the product answers its own question,
which is the claim the milestone is testing.

## 2. The worktree as a navigation object — cost in seams: real

### What the history says about how well a worktree is modelled today

Badly, and the codebase has already paid for it once.

- There is **no worktree entity anywhere in the renderer**. `AnySession`
  (`store.ts:138`) carries `projectId`, `projectName`, `projectPath` — and no
  branch, no worktree path, no worktree id.
- A worktree is modelled as a **cwd override**: `Persisted.termCwd`, commented
  *"Per-terminal working-dir override (e.g. a git worktree path)"*, resolved
  through `sessionCwd(termId)`. That is a string on a terminal, not an object.
- The launch toggle **defaults off** (`LaunchOptions.tsx:47`), and is offered
  from only one of its two callers.
- `buildOwnership` keyed on **project name** until `a0d925a` (2026-09-09), so
  *"two worktrees of one project conflicted on every shared path, defeating the
  worktree toggle entirely."* It now keys on `normDir(e.cwd)` — the normalised
  tree.

That last one is the whole lesson: **the bug was one identity used where two
were needed, and it shipped.** It was invisible to the typecheck, green in the
suite (five tests failed only after the fix was written), and was found by a
human in a 43-minute session in the real app. A worktree navigation object mints
a **third** identity axis on top of `projectId` and `normDir(cwd)`. The history
says the cost of an identity axis here is not the code that adds it; it is every
surface that later disagrees about which one it is using.

### How a main-origin worktree fact reaches a renderer nav surface

The crossing is **already shaped correctly, by accident**, and must stay that
way. `src/preload/index.ts:311` **re-declares** `interface Worktree` rather than
importing `src/main/worktrees.ts`. Facts cross as IPC payloads over
`git:worktrees` / `git:worktreeAdd` / `git:worktreeRemove`, and the renderer
reads the type from `window.api`, which R3 exempts wholesale. R1 and R2 are
satisfied by construction today.

Three rules keep it that way:

1. **`deck.ts` stays pure and synchronous.** `deriveDeckStrips` (`deck.ts:193`)
   takes sessions and returns strips; it has no IPC, no `async`, no store read.
   If it needs a branch, the branch is **handed to it**, as a field on the
   session or a lookup map passed as an argument. The moment `deck.ts` calls
   `window.api.git.worktrees(...)`, the codebase's one testable pure derivation
   becomes untestable — the same failure as `server.ts:29` wearing a different
   coat: a module reaching sideways for a fact instead of being given it.
2. **The poll gets its own store, like `folderStates.ts`.** Branch-per-cwd is a
   15-second git fact for N worktrees, not one project path (`DeckStatus.tsx`
   polls `git.status` for the active project only, today). Putting an N-way poll
   into the main store re-renders everything subscribed to it; `useFolderStates`
   exists for exactly this reason and even carries `sameStates` to keep the
   object identity stable between identical reports. Copy that shape, including
   the stability guarantee — a fresh object per poll is the render loop neither
   the build nor the typecheck catches.
3. **If the renderer needs the `Worktree` shape structurally, it goes to
   `src/shared/worktree.ts`**, imported by main and preload from there. Do
   **not** add a `renderer -> main` line to `ALLOWED_TYPE_EDGES`. That list
   already carries two such entries and names them, in its own comment, as
   "real debt".

### The third normaliser, which nobody has asked about

`ownership.ts:26` and `paths.ts:15` contain **byte-identical** path
normalisers — slashes folded forward, trailing separators stripped, lowercased —
written twice, both private to their module. One decides whether two agents
conflict; the other decides run-cost attribution.

A worktree navigation key is a **normalised path used as an identity**. It will
be the third copy, and it will be written by whoever implements the nav, in
whichever file they are in. When it drifts by one character — a UNC prefix, a
trailing dot, a drive-letter case — the deck groups one way and ownership groups
another, and the surface saying *"2 agents are already working in this tree"*
disagrees with the surface that put them in different rows. That is the
`buildOwnership` bug again, one level up.

**Fix before the nav work, not after:** promote the normaliser to
`src/shared/paths.ts` as one exported function; have `ownership.ts`, `paths.ts`
and any worktree key import it; and pin it with a renderer-wide scan asserting
that the normalising expression appears in no renderer file. Two hours, no new
dependency, and worth doing **whether or not the nav work happens** — it is a
live duplication today.

### The grouping key, and the pin it needs

`deriveDeckStrips` groups by `s.projectId`. `projectSessionCounts` (same file)
also keys by `s.projectId` and is what paints the attention count on every
`ProjectSwitcher` card. If the deck re-groups by worktree and the counts stay on
`projectId`, the deck shows four strips and the switcher card shows one number
covering all four — two populations, one apparent fact.

So: **one exported key function, both consumers.** Extract
`sessionGroupKey(session)` in `deck.ts`, have both call it, and pin the
partition rather than the call site — a behavioural test in `tests/deck.test.ts`
asserting that for any session list, the set of keys produced by
`deriveDeckStrips` equals the set of keys in `projectSessionCounts`. A source
scan would pass on two functions that happen to be spelled the same; this fails
when they diverge in meaning.

## 3. Reversibility — split both, the same way D1 was

### The merged palette: one piece, reversible

Pure renderer, two files, no persisted state, no IPC channel, no `window.api`
surface. Rollback is `git revert`. It needs no split. Keep `Ctrl+K` and
`Ctrl+Shift+P` both opening the merged surface for one release — a beta user's
muscle memory is the thing being changed, and two doors into one room costs
nothing.

### The worktree object: split, and the second half is the one to refuse

**W1 — the branch becomes visible. Reversible.** This is
`D1-orca-layout.md`'s own portable idea #3: the existing deck key's identity
line gains the branch name, only when a project runs more than one active
branch. Read-only, no new key, no new chrome, no persisted state, no grouping
change. It needs the poll store (rule 2 above) and nothing else. Revert is one
commit. **This delivers most of the user-visible value of "switching agent and
switching branch are one act"** — because the switch is already one act today
(the session *is* in the worktree, via `termCwd`); what is missing is only that
the user cannot *see* which.

**W2 — the branch becomes the grouping key. Not cleanly reversible, and this is
the part nobody has costed.** `Persisted` in `store.ts` holds `tabsByProject`,
`activeTabByProject`, `activePaneByProject`, `viewByProject` — four maps keyed
by `projectId`, plus `projectMru` as a list of project ids. Re-keying navigation
to a worktree axis either migrates those maps or leaves them keyed on an axis
the UI no longer uses.

**The rollback scenario, concretely.** A beta user hates the new nav. They are
running a packaged, auto-updating build with a real `workspace.json`. If W2
wrote `tabsByWorktree`, downgrading gives them a build that reads
`tabsByProject` — absent — and they open DevDeck to **no tabs, no active pane,
no view memory**, on the machine where their five-session first impression
lives. There is no migration-down path, and the only people who would hit it are
precisely the five people the milestone exists to get.

**So the rule for W2 is a hard one: it may not change any persisted key.** The
worktree axis must be derived at render time from `termCwd` plus the polled
branch map. If that is not enough to build the feature, the feature is not ready
and should wait until after the milestone, when a schema version and a migration
can be designed rather than improvised.

## 4. Would I refuse either?

**Not on structure, given the conditions above.** Both are shapeable into
something this codebase can keep paying for, and the merged palette is genuinely
cheap — it removes a surface rather than adding one, which is the direction the
product is travelling.

**On timing, I record an objection to both.** `ROADMAP.md`'s live section leaves
off, on purpose, *"every feature; any further UI, motion, colour or boundary
work; a fifth wave of pre-beta engineering under any name."* Both of these are
features. Neither passes test 2 — a stranger's first session is not *wrong*
without them. The binding constraint is invitations sent, which is zero, and K6
fires on 2026-09-22. **Correct idea, wrong month.**

**And one thing I am not the seat for, but which must be written down before it
is decided by accident.** `ROADMAP.md`, ruling of 2026-09-11, defines what the
five sessions are testing: *"a **project** — not a repo, not a worktree — as the
unit of context."* W2 changes that unit. Doing it eight days before K6 means the
five recorded sessions measure a different product from the one the validation
criteria in `docs/beta/05-validation-criteria.md` were written against, and the
milestone's result becomes unattributable — a negative result would not
distinguish "the residue is unwanted" from "we changed the residue
mid-measurement". That is `product-director`'s call, not mine. It should be made
explicitly.

W1 does not have this problem. It makes a worktree *visible* without making it
the unit.

## Summary of rules to land

| # | Rule | Home | Cost |
|---|---|---|---|
| N1 | `wantKind` has exactly one caller, and it is `store.ts` | `tests/signalSites.test.ts` | ~30 min |
| N2 | One path normaliser, in `src/shared/paths.ts` | new module + `tests/signalSites.test.ts` | ~2 h, do regardless |
| N3 | `deriveDeckStrips` and `projectSessionCounts` partition identically | `tests/deck.test.ts` | ~1 h, only if W2 |
| N4 | No `renderer -> main` entry added to `ALLOWED_TYPE_EDGES` | `tests/architectureBoundaries.test.ts` (already enforced) | 0 |
| N5 | W2 changes no key in `Persisted` | no rule can catch this — see below | — |

**N5 is the one no test can catch**, and by this document's own method that is
the strongest argument against W2 in its current form. A persisted-schema change
is invisible to the typecheck, green in the suite, and only fails on a machine
that already has a `workspace.json` written by the other version — which is
never this one. The only instruments are a hand-written round-trip test against
a fixture `workspace.json` from the previous release, and not doing it.
