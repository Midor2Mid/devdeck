(`isPrivate: false`). `v0.13.0` exists on GitHub but `gh release list` reports it

## 1. Why has nobody been contacted — the real reason, not the stated one

The stated reason, visible in five weeks of commits, is a sequence of
"prerequisites": no build, no public repo, no signed certificate, seven UI
defects, a verification pass. Every one of those was true when written and every
one is now false or moot — `product-director` confirmed this on 2026-09-08 and
`pm` confirmed again that §1 of the recruiting message depends on none of them.
**The engineering blocker cleared four days ago and the silence continued
anyway.** That gap is the finding.

The real reason is that five agent seats can generate an unlimited supply of
legitimate-looking pre-beta work — a roadmap audit, a kill-criteria addendum, a
plan with fourteen tracks, a defect ledger, a design pass on a deck that hasn't
met a stranger yet — and every one of those tasks is comfortable in a way that
sending one DM to a real person is not. Writing code cannot reject you. A
stranger who installs your app and says "I don't get what this is for" can. The
org's structure (me included: I am one more seat producing one more document
right now) makes it trivially easy to keep the fear of that sentence one
plausible-sounding task away, indefinitely, while looking productive the whole
time. `product-director` named this exactly and gave it a number, K6, precisely
*because* it is the likeliest of six criteria to fire and the only one that
fires on the owner. I agree with that ruling and I am not going to soften it:
**the delay is the owner's, and no amount of additional analysis — including
this document — substitutes for the one action that unblocks it.**

## 2. The smallest honest first contact that could happen today

It already exists, unsent, at `docs/beta/02-recruiting-message.md` §1:

> I built a Windows app for driving claude/codex/gemini across several projects
> in one window, and nobody outside my machine has ever run it. Would you be up
> for installing it while I watch and say nothing for half an hour?

What a candidate is asked to do: reply "yes" in the same thread. Nothing else —
no file, no six-question intake, no install — happens until they say yes. What
comes back: a yes, a no, or silence, each of which is itself recorded
(`02-recruiting-message.md` §9 covers "no"; silence is `invited` with no reply
and gets an outcome written down at day 7, not left open).

The one correction to make before sending: pick the reply channel now
(`02-recruiting-message.md`'s own rule, and T1 Step 4 of the execution plan).
Given the constraints in §4 below, my answer is **reply in the same
thread/DM the candidate was reached through** — not a new channel, not an
email address invented for this. Say so in the message: *"reply here, or open
an issue on the repo if you'd rather it be public — either is fine."*

**Do not use §2** (the longer post) yet — it still pitches "an editor, an API
client and a database panel," which is the exact framing D1 is deleting and the
exact framing that would corrupt criterion S4 for the first person who reads it.
§1 carries no such claim. Send §1 today; hold §2 until the README correction
lands.

## 3. Where five candidates come from, and what it costs

The three-fact gate excludes almost everyone: real Windows shell, a daily agent
CLI, more than one repo in flight (`docs/beta/01-who-to-approach.md`). That is
deliberate — it is also why this is not a five-minute recruiting job.

Concretely, today, in order of fidelity:

- **Archetype A (professional network).** Current or former colleagues and
  client-team developers on Windows who have started leaning on `claude`/`codex`.
  Highest-fidelity because they can be watched in person or on a call they'd
  take anyway. This is where the *first* invitation should go — it is the
  fastest path to a "yes" and the lowest-stakes rejection.
- **Archetype B (public complaints).** A live search today for a Windows-specific
  agent-CLI complaint: issues on `anthropics/claude-code`, `openai/codex`,
  `google-gemini/gemini-cli` filed by someone visibly on Windows (mentions
  PowerShell, `%APPDATA%`, `.exe`, WSL path translation); `r/ClaudeAI` and
  `r/ChatGPTCoding` threads where the poster names Windows. Reply once, in that
  thread, about that problem — never broadcast.
- **Archetype C (multi-agent power users).** Threads about worktree-per-agent
  habits or "I lose track of which agent is waiting," in the same trackers plus
  the Claude developer Discord.
- **Archetype D (WSL/Git Bash), one or two slots only.** Same channels, filtered
  for "I do everything in Git Bash" or "WSL is my daily driver."

**The cost, stated plainly because the docs already pre-registered it:** K1 sets
the honest budget — approach at least **15 gate-qualified candidates**; if fewer
than 5 accept a session, that is a kill signal about the target user's rarity,
not a recruiting failure. `pm`'s own plan names 6–8 as the day-one target so
sourcing runs ahead of the one-at-a-time cadence. Five *recorded sessions*
realistically costs on the order of **10–15 approaches** once declines, silence,
and disqualified-at-intake candidates are subtracted — which is why H2 says
"name six to eight and send the first message" rather than "name five."

## 4. The reply-address problem

**My answer: reuse the channel that recruited them — DM, Discord, or whichever
thread — with "open a GitHub issue on the now-public repo" offered as an
explicit alternative, and nothing else stood up.**

Why not a new dedicated email or a signup form: it is a single-maintainer,
no-account, no-telemetry product, and standing up new infrastructure to receive
five people's bug reports is exactly the "fifth piece of pre-beta engineering"
`product-director` refused in advance. It would also be one more task that isn't
the DM.

Why not *only* the GitHub issue tracker, even though the repo is public now:
the diagnostics record contains file paths and command lines from the
candidate's real repos (redacted of secrets, not of structure), and
`03-install-watch-protocol.md`'s ask — *"delete a line you'd rather not
send"* — assumes the candidate controls who sees it. A DM keeps that default
private; a public issue does not, and a stranger who has just met a self-signed
installer and a SmartScreen wall is not the moment to also ask them to post
their project layout in public. Offering the issue as an *opt-in* alternative
respects a candidate who'd rather it be discoverable (some will), without
making publicness the default.

This also answers itself economically: whichever platform reached the candidate
already has the maintainer's attention on it, costs no new signup, and scales
fine for 5–10 people without a queue or triage system nobody asked for.

## 5. What the first session must capture to be evidence

Already specified in `04-session-record-template.md` and I am not going to
re-invent it, only state the bar for refusal:

**I would refuse to count a session if:**
- No verbatim quote exists — a paraphrase written the next day, however
  confident, is a fabricated quote the moment it appears in quotation marks.
- The author (any agent standing in for them) explained, demoed, or named a
  feature before the candidate found it themselves. That candidate's first five
  minutes are permanently spent; no later session with them can substitute.
- The candidate is the author, or anyone who has already seen the app.
- A **[required]** field in the template is blank when the record is pasted
  into `NOTES.md` — no funnel state, no timestamped stall list, no defect
  ledger row for anything that blocked them.
- The record was written more than "within one hour" after the call and
  presented as if it weren't reconstructed.
- A coached moment is folded into the record without the `COACHED at mm:ss —
  I said: "..."` stamp that marks everything after it as weaker evidence.
- Silence (never reopened, no reply to day 7/14) is quietly omitted rather than
  written down as the result it is.

What makes it evidence rather than an anecdote is exactly the three-way split
the brief asks for — did / said / I-think-it-means — enforced per-session, not
summarized across sessions until `po` writes the milestone verdict.

## 6. What to watch for

- **The shell-mismatch false negative, specifically** — a Git Bash or WSL user
  (archetype D) sees `NOT ON PATH` on a launcher card for an agent that runs
  fine in their actual shell. This is the one pre-registered case that produces
  *wrong* information rather than *no* information, and per
  `06-shell-mismatch-watch.md` it is a stop-the-line (L2) event the first time
  it causes someone not to launch, or the second time it's merely seen. Do not
  warn the candidate about it in advance — that destroys the only observation
  it exists to produce.
- **The empty Releases page**, if anyone follows the README before the build is
  hand-delivered — a stranger who goes looking on their own, ahead of the
  session, meets a draft release with nothing attached. Say so in the delivery
  message rather than letting them discover it.
- **The residual `WORKING` blip (~6s)** on re-entering an agent's tab, confirmed
  in this week's QA pass. If a candidate reads a finished turn as still running
  and reacts to it (waits, re-asks the agent, or comments that the app is
  lying), that is a live instance of the one disclosed-but-unfixed defect —
  record it as `wrong-info` in the defect ledger, not as cosmetic, and note
  whether it changed what they did.
- **Whether they ask where the Database/API/Network panels are** — the
  falsifier for D1's authorized deletion. It can still fire even though D1 no
  longer waits on it; if it does, `po` needs it regardless of ordering.
- **The SmartScreen wall itself** — K4's entire test. Whether they pause, read
  the warning aloud, check the SHA-256, or abandon there.
- **Silence as a result** — a candidate who installs and never reopens is the
  single most informative outcome available and the easiest one for an eager
  narrator (me included) to leave out of a report in favor of the session that
  went well.
