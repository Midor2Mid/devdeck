A cockpit for the projects you already have.

DevDeck is a terminal-first workspace for developers who spend the day driving Claude Code (or Codex, or Gemini) across more than one project. Pick a project and every terminal and agent session snaps to it, side by side, labeled, running even when you switch away. One deck shows every project's agents at once, and which one is waiting on you.

Where this is

Not launched. Not asking for installs.

This page exists mainly to carry the code-signing policy below — it's a requirement of applying for a trusted certificate, not a sign that DevDeck is finished being tried. Nobody outside the machine that built it has run this app yet. If that changes, it'll be a handful of people at a time, not an install count. If you want to be one of them, say so on Issues.

What it does

  • Terminals. Multiple tabbed, split real shells — PowerShell, cmd, Git Bash, WSL — via a real pty, each rooted in a project's folder. Sessions survive a project switch; killing one is explicit.
  • Agent sessions. Launch Claude, Codex, Gemini or a custom CLI per project. Status (working / idle / needs attention) comes from output activity and the terminal bell, not from parsing what the agent prints.
  • Editor. Monaco: file tree, tabbed files, syntax highlighting, save. Not a replacement for a full IDE — no language servers, no debugger.
  • API client. A Postman-style request builder that sends from the main process, so there's no browser CORS wall. Collections, history, response tests, and cURL paste-to-parse.
  • Database. Saved connections for PostgreSQL, MySQL, SQL Server and SQLite. A SQL editor and a results grid. Passwords are encrypted at rest.
  • Browser. An embedded browser with a comment mode that hands an agent the element you clicked, the console errors, and the failed requests around it.
  • Remote. An optional, token-gated web client so you can watch and drive a session from a phone. Off by default; nothing binds to the network until you turn it on.

Windows only

That's a position, not a gap. DevDeck runs on Windows because that's where it gets used and the only platform it's ever been tested on. There's no "macOS and Linux coming soon" — if that changes it'll be because a Mac or Linux user showed up and said they needed it, not because it was always the plan.

Source and releases

Both live on GitHub. The current version is 0.13.0 — see the changelog for what actually shipped in it and every release before it.

About the installer: builds today are signed with a personal, self-signed certificate — enough to satisfy this one machine, and nothing more. Run one anywhere else and Windows SmartScreen will warn you before you can open it, because it has no reason yet to trust the signer. That's expected, not a bug. See code signing policy for what's being done about it.

Code signing policy

DevDeck's release builds are produced with electron-builder and signed. Today that signature is a self-signed Authenticode certificate made on the machine that builds them — it stops the loudest antivirus false positives locally and is trusted by no other Windows install.

The plan for clearing SmartScreen is a free, trusted certificate for open-source projects from the SignPath Foundation, via SignPath.io. To be exact about where that stands: it has not been applied for yet, because the Foundation requires a public repository and this project's repository is still private. So there is no pending application and no granted certificate — only an intention, and a release pipeline with the signing step already built and waiting. Team roles

One person works on DevDeck. Raymond Tran writes, reviews, and merges everything that ships — committer, reviewer and approver are the same person. See the commit history for that in practice.

Privacy

DevDeck's Remote server is off by default, and requires a token even when it's turned on. Its diagnostics record (Settings → About → Copy diagnostics) is copied to your clipboard — it is never transmitted anywhere, by anything, under any circumstance. The one thing DevDeck fetches on its own is a check against GitHub's release feed at launch, to tell you if a newer version exists; that request carries nothing about you or your project. Nothing else leaves this app without you asking it to.

Issues & pull requests

Bug reports and problems go in Issues on GitHub. Discussions are off — there's one maintainer, and a tracker is enough surface for that.

Pull requests are welcome for exactly one thing: fixing behavior that's already shipped. Open an issue first and it'll get a yes or no before you spend time on a patch. This isn't where new features get decided — that happens against the roadmap, not a PR queue.
